## Chapter 1 问题描述

### 1.1 实验目标

本实验以 MIT 网站提供的莎士比亚全集为检索语料，实现词频统计、停用词识别、词干化倒排索引和查询处理，并分析阈值变化对索引及查询结果的影响。Bonus 部分考察 500,000 个文件与 400,000,000 个不同词条件下的可扩展性。

每个文本文件对应一个文档。程序按输入文件顺序分配从 0 开始的文档 ID，并返回单词或短语所在的文档及位置。除题目要求外，程序支持多查询单元的 AND 运算。

### 1.2 语料及统计口径

语料取自 MIT 目录的 42 个条目，包括 37 部戏剧与 5 个诗歌集合；154 首十四行诗合并为一个文档。源网站及其公开镜像见参考文献 [1]。镜像版本为 `6b82db852c7322dd33e95db347f0ddfc812c6409`。

预处理删除 HTML 标签、网页导航和广告，保留场次标题、角色名及舞台说明。戏剧从首个 `<h3>` 标签开始提取，诗歌提取正文可见文本。`elegy.html` 中的 `</TITLE` 标签缺少结束符，对该标签补全后提取正文，文本内容未作修改。

采用 ASCII 字母与数字的连续段作为 token，并转换为小写。撇号及连字符作为分隔符，例如 `don't` 分为 `don` 和 `t`。一个词在文档中的位置按完整 token 序列编号，起始位置为 0；删除停用词后保留原位置编号。当前实现的 token 缓冲区为 256 B，超过 255 B 的字母数字连续段截取前 255 B，仍计为一个 token；这一实现限制应与无限长度分词模型区分。

全集共有 **956,647 个 token、23,871 种原词形和 14,986 个词干**。其中，cf 表示词干的总出现次数，df 表示包含该词干的不同文档数，N 表示全部文档数。空文档也计入 N。

原始 HTML、提取文本、文档清单及 SHA-256 校验值位于 `test_data.zip` 的 `data/shakespeare/` 目录。各文档 ID 与作品名的对应关系见 `documents.csv`。

## Chapter 2 数据结构与算法

### 2.1 词频统计与停用词

统计与建索引采用两遍扫描。第一遍对全部词执行 Porter 词干化，建立包含全部位置的临时倒排索引；由位置总数得到 cf，由有序位置链中不同文档 ID 的数量得到 df，并按下式确定停用词：

```text
df / N > θ
```

默认 θ=0.5。高文档频率的词在文档间区分能力较低，因此用文档覆盖率划分 noisy words。该判据具有可重复性，但不等同于语义判断；例如 `love` 也可能因覆盖文档较多而被过滤。阈值实验用于考察索引大小与可检索内容之间的取舍。

第一遍生成 `stoplist.txt` 后释放统计索引；第二遍重新读取语料，剔除停用词并写出位置倒排索引。`--count-only` 只执行统计阶段，不生成索引文件。每遍扫描均对原始 token 执行一次词干化，查询也对输入 token 执行一次词干化；向索引插入已生成的词干时不再重复处理。词干模块采用文献 [2] 的 C 实现，许可及版权声明附于 `code/LICENSE-stmr.txt`。

#### 算法 1：词频统计与停用词识别（Word Counter）

输入为有序文档序列 D 和合法阈值 θ∈[0,1]，输出为词干统计表及停用词集合 S。以下伪代码按当前实现描述，统计阶段确实保存位置，并非仅维护计数器。

```text
WORD_COUNTER(D, θ)
    I ← 空哈希倒排索引
    for d ← 0 to |D|−1:
        将 d 加入 I 的文档表                  // 空文档也登记
        p ← 0
        for token in TOKENIZE(D[d]):
            w ← PORTER(LOWERCASE(token))
            向 I[w] 有序插入 (d, p)           // 插入失败则终止
            p ← p + 1
    N ← I 的文档数
    S ← 空集合；Stats ← 空统计表
    for each 词条 w in I:
        cf ← I[w] 的位置节点数
        df ← 扫描 I[w] 的位置链，统计不同 doc_id 数
        向 Stats 添加 (w, cf, df)
        if N > 0 and df / N > θ:
            向 S 添加 w 的字符串副本
    将 S 按词干排序，以支持后续二分查找
    按 df 降序、cf 降序及词干次序组织停用词输出
    写出 stoplist.txt；按运行模式输出统计结果
    return I, Stats, S
```

`--count-only` 在完成上述阶段后结束。正常建索引时先完成统计输出，再释放第一遍的临时索引；停用词字符串独立保存，供第二遍扫描使用。

### 2.2 内存结构与文件格式

词典采用 1,000,007 个哈希桶，以链地址法处理冲突。每个词条保存词干、tf、位置链表头及哈希冲突链指针；位置节点记录 `(doc_id, pos)`，按文档 ID 与位置升序排列。文档表为升序、无重复的 ID 数组。内存中的 df 通过扫描位置链计算；磁盘词典另外保存 df 和 tf，便于加载时交叉校验。全文 cf 指语料中的词干总频次，词条字段 tf 指该词干位置链的节点总数，并非单篇文档的词频。对于保留词干，两者相等。

`index.bin` 使用小端定长整数及 LEB128 变长编码。文件由连续的头部、文档表、词典和位置段组成。

| 部分 | 保存内容 |
| --- | --- |
| 头部（64 B） | 魔数、版本、文档数、词条数、位置总数及三段偏移 |
| 文档表 | N 个 u32 文档 ID |
| 词典 | u32 df、u32 tf、u64 文件绝对偏移、u16 词干长度及词干字节 |
| 位置段 | 文档增量、文档内出现次数与位置增量，采用 LEB128 编码 |

加载器检查魔数、版本、段边界、词典与文档表顺序、df/tf、累计位置数和文档引用，并在增量累加前检查整数范围。该格式未设置校验和，因此无法识别所有仍满足结构约束的内容改动。构建结果先写入临时文件，再替换目标索引；Windows 使用 `MoveFileExA`，POSIX 使用 `rename`。

#### 算法 2：位置倒排索引生成（Index Generator）

输入为相同顺序的文档序列 D 和算法 1 产生的停用词集合 S，输出为 `index.bin`。位置计数器随每个原始 token 递增，不能仅对保留词递增。

```text
INDEX_GENERATOR(D, S)
    I ← 空哈希倒排索引
    for d ← 0 to |D|−1:
        将 d 加入 I 的文档表
        p ← 0
        for token in TOKENIZE(D[d]):
            w ← PORTER(LOWERCASE(token))
            if 二分查找 S 未找到 w:
                向 I[w] 按 (doc_id, pos) 顺序插入 (d, p)
                若插入失败，则终止构建并报告错误
            p ← p + 1
    Terms ← 收集 I 的词条并按词干升序排列
    for each w in Terms:
        按文档分组，对文档 ID 和位置进行差分与 LEB128 编码
        计算该词位置段的长度及文件绝对偏移
    向临时文件写入头部、文档表、词典及编码位置段
    若写入或关闭失败，则删除临时文件并返回错误
    用临时文件替换 index.bin；替换失败则报告错误
    return 成功
```

源码的 `index_save` 先编码以确定各词位置段长度，再编码写出数据；复用单词条编码缓冲区，无须同时保留全部词条的编码副本。

### 2.3 查询处理

查询采用与建索引相同的分词与词干化规则。单词查询返回 df、tf 和命中位置；AND 查询对各单元的升序文档列表求交。

短语查询先求候选文档交集，再选择 tf 最小词的原始下标 anchor 作为锚点。候选起点为该词的命中位置减去 anchor，并逐词验证 `start+i` 是否存在。该过程保持原短语词序，允许重复词。

命令行中的多个参数表示 AND；单个参数中的多个 token 表示连续短语。`test.txt` 的普通行表示 AND，`phrase:` 行表示短语。每次查询结果写入 `output.txt`。查询最多包含 32 个单元，每个短语最多 16 个词；超出限制的输入返回错误。

查询阈值 τ 对每个查询词干分别检查。满足下式时，程序输出该词干的 df、tf 等统计信息，并将该词标为不可用于本次结果列表：

```text
df / N > τ
```

θ 与 τ 均采用严格大于条件，相等时不触发过滤或抑制。θ 决定索引中的词条，τ 控制查询词能否参与结果展示。当前实现中，任一必需词未入索引或被 τ 抑制，对应短语单元返回空文档集；多单元 AND 因此也返回空集。τ 不作用于最终 AND 或短语的整体命中文档比例，也不改变磁盘索引。已删除停用词的位置无法由当前索引恢复，因此包含这些词的精确短语不能直接检索。

#### 算法 3：查询处理（Query Processor）

输入为已加载的索引 I、查询单元序列 U 及可选阈值 τ，输出为单元的命中文档与位置，以及多单元 AND 的文档交集。命令行和文件输入首先按第 2.3 节的规则解析为 U。

```text
QUERY_PROCESSOR(I, U, τ)
    若单元数超过 32，则返回错误
    for each 单元 u in U:
        W ← 对 u 分词，每个 token 转小写并执行一次 Porter 词干化
        若词数超过 16，则返回错误；若无词，则该单元结果为空
        usable ← 真
        for each w in W:
            查找 I[w]
            若不存在：输出缺失或停用词提示；usable ← 假
            否则：由位置链得到 df、tf，输出统计信息
                  若设置 τ 且 N > 0 且 df/N > τ：
                      输出 Too common；usable ← 假
        if usable 为假:
            Docs[u] ← 空集；continue
        if u 为单词单元:
            Docs[u] ← I[W[0]] 中升序去重的文档 ID
            对独立单词查询输出其全部 (doc_id, pos)
        else:
            C ← W 中各词的文档 ID 列表之交集
            anchor ← tf 最小词在 W 中的原始下标
            Hits ← 空列表
            for each d in C:
                P[i] ← W[i] 在文档 d 中的升序位置数组
                for each p in P[anchor]:
                    start ← p − anchor
                    若 start < 0，则跳过
                    若对每个 i，start+i 均未溢出且可在 P[i] 二分找到：
                        向 Hits 添加 (d, start)
            输出 Hits；Docs[u] ← Hits 中升序去重的文档 ID
    若 U 含多个单元：输出所有 Docs[u] 的交集
```

正确性依据如下：单词位置直接来自索引；AND 的命中文档必须出现在每个单元的文档列表中。对于短语，任一真实起点 s 必有锚点位置 s+anchor，因此会被枚举；候选起点只有在所有 `s+i` 均存在时才被接受。锚点只改变候选枚举方式，不改变词序，重复词也按各自下标验证。这里的“精确”指分词和词干化后的连续 token 匹配，不保证原始词形、大小写或标点完全相同。

### 3.3 缺陷定位与修正

初次全集测试为 67 项通过、2 项失败。短语词数组按 tf 排序后，原程序仍按 `start+i` 检查位置，导致查询顺序改变。将排序改为保留词序的锚点选择后，真实短语及最小反例 `alpha beta alpha alpha gamma` 的起点均正确。

加载器原先要求最大 posting 文档 ID 等于文档表最后一个 ID，因而拒绝尾部空文档。现改为检查每个 posting 引用是否属于文档表，允许文档没有索引词。此外，普通文件查询改按 AND 处理，Windows 连续重建改用可替换已有目标的文件接口。

在后续 36 项补充回归中，修正前结果为 17 项通过、19 项失败，修正后全部通过。主要修改为：统一语料与查询分词；拒绝空值、NaN 及超范围阈值；拒绝过长查询行；补全单词结果的文档数组；验证词典及文档表的严格顺序；在增量累加前检查整数溢出；使用扩展整数计算 INT_MAX 位置的首个增量；位置节点分配失败时终止构建，防止成功保存不完整索引。

两阶段检查数量不同，分别对应不同的测试集合。修复记录、源码差异及修正前结果保存在压缩包的 `evidence/` 和 `results/review_*.json` 中。

## Chapter 4 复杂度、结果讨论与 Bonus

### 4.1 时间与空间复杂度

#### 4.1.1 符号与分析口径

设原始输入字节数为 B，token 数为 T，文档数为 N，第一遍词干数为 V，哈希桶数为 M=1,000,007，停用词数为 S。保留词干数为 V′，位置数为 P；词干 w 的原始总频次记为 f_w，保留词的频次记为 f′_w。令 L 为参与处理的最大词长，H 为词干字符串的总存储字节数，E 为编码后位置段的字节数。下述分析区分算法成本与磁盘 I/O，不将单次实测耗时作为渐进界的证明。

#### 4.1.2 统计与索引构建

逐字符分词需要 O(B)。设一次词干化的成本为 C_stem(L)，每遍的总成本上界为 O(T·C_stem(L))。Porter 实现分阶段检查后缀并原地改写，不枚举词典；其实际字符扫描成本取决于词长和具体规则，不能无条件当作与词长无关的常数。当前程序对词长设有固定上限，在本次规模分析中可将单次处理视为有界操作。

均匀散列下，词典平均链长约为 V/M，计入字符串比较后，第一遍哈希访问的期望成本为 O(T·L·(1+V/M))；严重碰撞时则可能退化到 O(T·L·V)。第二遍还要对每个词干二分查询停用词表，成本为 O(T·L·log(S+1))。

当前位置链从头开始有序插入。即使输入已经按文档与位置递增，第 j 次插入仍扫描此前的 j−1 个节点，因此一个频次为 f 的词需要：

```text
0 + 1 + … + (f−1) = f(f−1)/2
```

两遍位置插入的总成本为 O(T + Σ_w f_w² + P + Σ_w∈保留词 f′_w²)。由于第一遍保留全部位置，停用词过滤不能消除第一遍高频词的二次方开销。第一遍统计 df、收集词条和建立停用词集合需要若干次扫描，合计 O(M+V+T)，此外还包括统计排序与停用词排序。

设 K_sort(n,L) 为当前 C 运行库 `qsort` 对 n 个元素的实际排序成本。统计与保存中的排序成本包含 K_sort(V,L)、K_sort(S,L) 及 K_sort(V′,L)。若采用 O(n log n) 次比较的排序实现，字符串比较计入后可估计为 O(L·n log n)；C 标准接口本身不承诺统一的最坏时间界，因此不把这一估计写成跨运行库保证。

文档 ID 按升序登记，每次通过二分确定位置，总查找成本 O(N log(N+1))；本输入顺序下无需移动已有文档元素，扩容复制总量为 O(N)。保存阶段需要 O(M+V′) 的词条收集、词条排序，以及 O(P+E) 的差分编码与写出成本。位置段为测长和落盘编码两次，不改变其渐进阶。

综合以上各项，当前构建的主要退化来自 Σ_w f_w²，而非仅由 T、V 决定。若只有一个高频词，其位置插入就可达到 Θ(T²)。

#### 4.1.3 查询与加载

索引加载必须读取文件全部内容，并对解码位置逐次调用同一个有序插入接口，因此还包含 O(P+Σ_w∈保留词 f′_w²) 的链表重建成本，以及词典查找、文档表验证与 I/O 成本。索引文件紧凑并不意味着加载一定接近线性。

对于 k 个查询词，记其位置数为 f_i、文档数为 d_i。当前程序从位置链生成文档列表，需要 O(Σ f_i)。`intersect_docs` 使用单调前进的指针，并以首列表为候选来源；保守上界可写为 O(k·Σ d_i)。k 受固定上限约束时，可视为对列表总长度的线性处理，不能因此忽略此前的位置链扫描。

短语长为 m、候选文档数为 C。源码为每个候选文档从各词位置链的头部重新提取位置，最坏额外成本为 O(C·Σ f_i)。设锚点候选位置总数为 A，各词在文档 d 内的位置数为 p_i,d，则连续性验证的成本为：

```text
O(Σ_d p_anchor,d · Σ_i log(p_i,d + 1))
```

可用 O(A·m·log(f_max+1)) 作为简化上界。选择 tf 最小的锚点有助于减少 A，但不会消除重复扫描位置链的成本。输出结果另外需要与输出量成正比的时间。启动查询程序时索引全量加载一次；同一进程读取多行 `test.txt` 时可复用该索引，分别启动命令行查询则每次都支付加载成本。

#### 4.1.4 空间、外存与结果解释

第一遍临时索引占 O(M+N+V+H+T)，统计数组与停用词字符串也需空间；第二遍保留索引占 O(M+N+V′+H′+P)，并保留停用词表及统计数组。两份位置索引不同时驻留，故总峰值取各阶段内存之最大值，而不是简单相加。保存时另需 O(V′) 的词条、偏移及长度数组，以及最大单词条编码缓冲区。

磁盘空间可写为 64+4N+18V′+H_disk+E 字节，其中 H_disk 为不含字符串结束符的词干总字节数。查询除全量索引外还要分配文档、位置及结果数组；短语位置数组按各词全局 tf 分配，附加空间含 O(Σ f_i)，不是仅按当前文档的命中数分配。

第 3.4 节各 θ 的峰值 working set 接近，可由共同的第一遍全量统计阶段解释；提高 θ 主要增加第二遍索引和输出文件，未必显著改变进程峰值。构建时间不单调还受额外 token dump 和运行噪声影响，不能据这些单次测量断言更大的 θ 会加快算法。

SQLite 外存原型使用 B-tree。以树高 h 计，定位记录需沿树访问 O(h) 个页，插入还可能引起页分裂；其总成本同时受事务、缓存和磁盘 I/O 影响，不能将固定页缓存等同于整个进程的恒定内存。以下实测仅验证给定合成数据规模，四亿词部分单独标为估算。

### 4.4 四亿不同词的资源估算

本机测得 `sizeof(Posting)=32 B`、`sizeof(Position)=16 B`、`sizeof(long)=4 B`。假设每个不同词至少有一个位置，且词干字符串连同结束符平均占 16 B，则 C 索引载荷估算为：

```text
8,000,072 + 500,000 × 4 + 400,000,000 × (32 + 16 + 16)
= 25,610,000,072 B ≈ 25.610 GB ≈ 23.85 GiB
```

该估算计入文档表的最低载荷，不含其预留容量、分配器开销、碎片、统计数组、排序数组及重复位置。现有词典每条固定元数据占 18 B，四亿条仅元数据即占 7.2 GB，尚未计入字符串与位置段。固定哈希桶下平均链长约为 400，查询常数也将显著增大。

当前加载器使用 `ftell/fseek` 与 long 偏移，本机 `LONG_MAX=2,147,483,647`，无法可靠处理超过约 2 GiB 的索引。命令行接口也存在限制：将 500,000 个文件名作为参数时，实际进程创建返回 WinError 206，程序尚未开始读取文件。该测试未创建实体文件。

因此，**当前 C 实现不能直接支持题目给出的完整 Bonus 规模**。文档 ID 的表示范围足够，但内存驻留、链表插入、全量加载、命令行长度及文件偏移均构成约束。

### 4.5 改进方向

输入接口可改为目录或文件清单，逐个读取文档。统计阶段可只累计 cf，并利用按文档顺序扫描时的最近 doc_id 更新 df，避免为统计保存全部位置；词典超出内存时，应按内存预算分块，再外部归并得到全局 df；确定停用词后，再对保留词构建分块位置索引。SPIMI／BSBI 分块与多路归并可减少一次性内存需求 [3]。

词典可采用磁盘 B-tree 或分块有序文件，文件访问改为 64 位偏移，查询时只读取目标词的位置列表。高频词的位置构建可采用尾指针或顺序缓冲，避免重复遍历。SQLite 原型验证了将词典与位置存盘的可行性，但未验证四亿不同词、五十万实体文件或一般高频语料；完整规模仍需进一步实验。
